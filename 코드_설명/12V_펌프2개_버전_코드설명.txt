================================================================
 코드 설명 — 12V 펌프 2개 버전 (A보드 + B보드)
================================================================
대상 코드 : A_board/A_board.ino , B_board/B_board.ino
구성      : 펌프1(급수)·펌프2(순환) 둘 다 12V DC 펌프 + 220V 히터
            ESP32 2보드 + 안드로이드 앱(BLE)
작성 목적 : "왜 이런 식으로 코드를 짰는가" 설계 의도 정리


[ 0. 큰 그림 — 왜 두 보드로 나눴나 ]
----------------------------------------------------------------
- A보드 = 센서 전담, B보드 = 제어/통신 전담으로 역할 분리.
  · 이유: 아날로그 센서 측정(ADC)과 무선(WiFi/BLE)을 한 칩에서 전부
    돌리면 ADC 노이즈, RAM 부족, 타이밍 충돌이 심해진다.
    역할을 나누면 각 펌웨어가 단순해지고 고장 원인 추적이 쉽다.
- 보드끼리는 ESP-NOW(WiFi 라디오, 채널1 고정)로 직접 통신.
  · 이유: 공유기/핫스팟 없이도 보드 간 저지연·자동 재연결.
    수조처럼 네트워크가 불안정한 환경에 적합.
- 폰은 B보드에만 BLE로 붙는다.
  · 이유: 제어 명령과 상태 표시는 B보드가 모두 쥐고 있으므로,
    앱은 B보드 한 곳만 보면 된다. A보드는 무선 송신만 담당.


[ 1. A보드 (A_board.ino) ]
----------------------------------------------------------------
(1) 아날로그 센서를 전부 ADC1(IO32~35)에만 연결한 이유
    - ESP32는 WiFi 라디오가 켜지면 ADC2 핀의 analogRead가 불안정/불가.
    - ESP-NOW는 WiFi 라디오를 쓰므로, 송신을 켠 상태에서 ADC를 읽으려면
      반드시 ADC1(IO32~39)을 써야 한다.
    - 그래서 조도=IO33, 탁도=IO32, pH=IO34, 수위=IO35 로 배치.
      (IO34/35는 입력전용 핀이라 센서 입력에 딱 맞음)

(2) analogAvg()로 16회 평균을 낸 이유
    - pH/탁도 같은 아날로그 값은 한 번 읽으면 출렁인다.
    - 짧은 간격으로 여러 번 읽어 평균 → 노이즈를 소프트웨어로 1차 제거.
    - (하드웨어 필터 커패시터와 함께 쓰면 값이 훨씬 안정)

(3) 12bit 해상도 + ADC_11db 감쇠를 설정한 이유
    - analogReadResolution(12): 0~4095 풀 분해능 사용.
    - ADC_11db: 약 0~3.3V 입력 범위를 받기 위함(감쇠 최대).
      → 분압 거친 센서 신호(최대 ~3.3V)를 안전하게 측정.

(4) DS18B20(수온)에 4.7k 풀업 + 유효범위 체크를 둔 이유
    - DS18B20은 1-Wire 통신이라 데이터선에 풀업 저항이 필수.
    - 읽은 값이 -50~85℃ 밖이면(특히 -127℃) 센서 미연결/배선 불량으로 보고
      dsOk=false 처리하고, 직전 정상값(lastValidTemp)을 유지한다.
      → 센서가 잠깐 튀어도 제어가 엉키지 않게 하는 안전장치.

(5) 5V 센서(탁도·pH·수위)에 분압 + 코드 복원(DIV=1.5)을 쓴 이유
    - 이 센서들은 5V로 동작하고 출력도 3.3V를 넘을 수 있다.
    - ESP32 ADC 최대 입력은 3.3V → 그대로 넣으면 핀 손상.
    - 그래서 10k+20k 분압(약 ×0.67)으로 낮춰 입력하고,
      코드에서 ×1.5(=1/0.67)로 실제 전압을 되돌린다.

(6) pH 계산식과 0~14 클램프를 둔 이유
    - pH7 기준전압(PH_NEUTRAL_V=2.50)과 기울기(PH_SLOPE=0.18)로
      전압→pH 환산. pH_offset으로 보정 여지를 둠.
    - 환산 결과가 0 미만/14 초과면 잘라낸다(클램프).
      → 노이즈로 말도 안 되는 pH값이 앱/제어로 넘어가는 것 방지.

(7) 수위(XKC-Y25-V)를 digitalRead + 반전 처리한 이유
    - 비접촉 수위센서는 사실상 ON/OFF(디지털) 신호.
    - 물이 차면 LOW로 떨어지는 동작이라, 코드에서 반전해
      1=정상(물참) / 0=부족 으로 직관적으로 맞춤.

(8) 16x2 LCD를 5페이지로 돌려 보여준 이유
    - 16x2 글자 LCD엔 수온/pH/탁도/조도/수위 5개를 한 번에 못 띄운다.
    - 그래서 한 화면에 하나씩, 2초마다 페이지를 넘긴다.
    - 주기적으로 lcd.begin()을 다시 호출 → 전기 노이즈로 LCD가
      깨졌을 때 자동 복구.

(9) READ_INTERVAL=2초로 한 이유
    - 너무 자주 읽으면 LCD가 어지럽고 노이즈에 민감, 전송도 과함.
    - 2초면 수조 변화 추적에 충분하면서 안정적.

(10) SensorData 구조체를 그대로 ESP-NOW로 보낸 이유
    - {수온,조도,탁도,pH,수위}를 한 구조체로 묶어 바이너리 전송.
    - B보드가 "똑같은 구조체"로 받으면 파싱이 필요 없다(memcpy).
    - 단, 양쪽 구조체 정의가 100% 같아야 함(중요).

(11) 부팅 진단(raw ADC) 출력을 넣은 이유
    - 시리얼에 각 센서 raw값을 찍어, 0 또는 4095(최대)면
      그 센서 신호선이 안 닿은(floating) 상태임을 바로 알 수 있다.
    - 배선 단계에서 어느 선이 문제인지 빠르게 잡으려는 디버그용.


[ 2. B보드 (B_board.ino) — 12V 펌프 2개 ]
----------------------------------------------------------------
(1) ESP-NOW 수신 + BLE 서버를 "동시에" 돌린 이유
    - A보드 센서값은 ESP-NOW(WiFi)로 받고, 폰엔 BLE로 보내야 한다.
    - 그래서 WiFi 라디오와 BLE를 한 칩에서 같이 켠다.

(2) 기본 BLE 대신 NimBLE를 쓴 이유
    - WiFi + BLE를 동시에 켜면 RAM이 빠듯하다.
    - NimBLE는 기본 Bluedroid보다 RAM을 훨씬 적게 써서 동시 동작이 안정.

(3) Nordic UART(UART 서비스) UUID를 쓴 이유
    - 앱과 약속된 표준 형태(주고받기 쉬운 RX/TX 특성).
    - status(notify)=보드→앱 상태 / cmd(write)=앱→보드 명령 으로 단순화.

(4) 상태 JSON을 20바이트씩 쪼개 notify한 이유
    - BLE 기본 MTU가 작아(약 20여 바이트) 긴 JSON을 한 번에 못 보낸다.
    - 20바이트씩 잘라 보내고 끝에 줄바꿈(\n)을 붙여,
      앱이 \n 기준으로 다시 합치게 한다.

(5) 명령을 "key=value" 텍스트로 받은 이유
    - heaterMode=2, tempSet=25.5 처럼 사람이 읽기 쉽고 확장도 쉽다.
    - 파싱이 단순(= 기준 split)하고 앱 구현도 간단.

(6) 각 장치 모드 0/1/2(끄기/켜기/자동) 구조로 한 이유
    - 사용자가 수동 강제(끄기/켜기)와 자동을 자유롭게 선택하게.
    - 자동(2)일 때만 센서/타이머 기반 로직이 작동.

(7) 히터 자동에 히스테리시스(tempSet ± tempHyst)를 둔 이유
    - 목표온도 근처에서 켜짐/꺼짐이 빠르게 반복(릴레이 채터링)되는 것 방지.
    - 목표-0.5℃ 아래면 ON, 목표+0.5℃ 위면 OFF 로 여유 구간을 둠.

(8) 펌프1(급수)=수위 기반, 펌프2(순환)=타이머 기반으로 나눈 이유
    - 급수는 "물이 부족할 때만" 채워야 하므로 수위센서에 연동.
    - 순환은 주기적으로 돌리면 되므로 시간(circOn/circOff) 기반.
      (둘 다 12V DC 펌프라 릴레이 CH1/CH2로 동일하게 ON/OFF만 함)

(9) 산소(oxygen)를 핀 없는 "로직 전용"으로 둔 이유
    - 12V 2펌프 버전에선 산소 출력 핀을 따로 두지 않았다.
    - 모드/타이머 상태값만 유지(앱 표시용). 실제 출력은 안 함.

(10) RELAY_LOW_TRIG / drive() XOR 처리를 둔 이유
    - 시중 릴레이 모듈은 대부분 LOW일 때 ON(액티브 로우).
    - drive(pin,on)에서 (on ^ RELAY_LOW_TRIG)로 극성을 한 곳에서 처리 →
      릴레이가 반대로 동작하면 상수 하나만 바꾸면 됨.

(11) A보드 신호 15초 끊기면 히터 자동 OFF (haveData 타임아웃)
    - 통신이 끊겨 수온을 모르는데 히터를 계속 켜두면 위험(과열).
    - 마지막 수신 후 15초가 지나면 haveData=false → 히터 강제 OFF.
      → 가장 중요한 안전장치.

(12) 부팅 시 채널별 1초 자가테스트를 한 이유
    - 펌프1→펌프2→히터 순서로 잠깐 ON 해보며 배선/릴레이를 점검.
    - 시작 시 전 채널 OFF로 초기화해 의도치 않은 동작 방지.


[ 3. 요약 ]
----------------------------------------------------------------
- 핵심 원칙: "A=측정 / B=판단·제어"로 단순 분리, 무선은 ESP-NOW+BLE.
- 12V 펌프 2개는 둘 다 저전압 DC라 릴레이로 그냥 ON/OFF만 하면 됨.
- 안전 우선: 통신 끊김 시 히터 OFF, 시작 시 전부 OFF, 값 튐 방어.
- 이 버전에서 펌프2(순환)도 12V DC였다는 점이, 220V 교체 버전과의
  유일한 실질 차이다. (코드 로직 자체는 거의 동일 — 다음 파일 참고)
