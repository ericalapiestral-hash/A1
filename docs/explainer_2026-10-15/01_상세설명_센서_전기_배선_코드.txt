============================================================
0. 이 자료에서 가장 먼저 구분해야 할 것
============================================================

이 장치는 ESP32 보드 두 개를 이용하는 수조 모니터링·제어 장치입니다.
A보드는 센서를 읽고, B보드는 그 정보를 받아 앱과 LCD에 보여주며 펌프를 제어합니다.

그런데 저장소에는 서로 다른 시기의 코드가 함께 있습니다.
폴더 이름에 A보드/B보드라고 적혀 있다고 모두 현재 장치에 설치된 코드는 아닙니다.
이번 설명의 실제 제어 기준은 B_board_Aquarium 폴더입니다.

[확인된 범위]
  - 사용자가 순환 v1.0.1 설치 후 실제 순환펌프의 켜기·끄기와 앱 제어가 정상이라고 확인했습니다.
  - 급수를 수동으로만 사용하려고 앱 v1.3.8과 B v1.1.0을 배포했습니다.
  - B v1.1.0의 급수·순환 코드, 빌드, 앱 테스트, 모의 설치·복원은 검증했습니다.
  - 현재 대화에서는 급수 v1.1.0의 설치 완료와 실제 급수 작동 결과는 아직 전달받지 못했습니다.
  - 따라서 '현재 실제 장비에 반드시 v1.1.0이 설치돼 있다'고 단정하지 않습니다.

[아직 실물 확인이 필요한 범위]
  - 실제 A보드의 원본 Arduino 소스는 없습니다.
  - A 센서의 실제 GPIO, 센서 정확한 제품명, 공급 전압, 센서 보정 상태는 미확인입니다.
  - 급수펌프는 B보드에 연결됐다고 확인했지만 실제 IN 선이 GPIO16인지와 극성은 현장 확인이 필요합니다.
  - 릴레이의 정확한 모델·채널 수·NO/NC 사용 접점, 펌프 정격 전압·전류는 미확인입니다.
  - 사진으로 실물 배선을 촬영한 자료는 제공되지 않았습니다.

첨부 PNG는 소스와 확인된 정보로 그린 설명용 배선도입니다. 실물 사진이나 전체 실측 회로도는 아닙니다.
그림에 '확인 필요' 또는 '원리 예시'라고 적힌 부분을 실제 확정 연결로 설명하면 안 됩니다.
특히 센서 핀과 펌프 전압을 모르는 상태에서 예전 그림을 그대로 보고 재배선하지 않습니다.

1. 장치 전체를 한 문장으로 설명하기
============================================================

“A보드가 수조의 센서 정보를 측정해 B보드로 보내고, B보드는 스마트폰과 정보를 주고받으면서
릴레이를 통해 펌프를 켜거나 끄는 장치입니다.”

역할을 사람에 비유하면 다음과 같습니다.
  센서 = 물 상태를 살펴보는 눈과 귀
  A보드 = 센서의 말을 숫자로 정리하는 측정 담당자
  ESP-NOW = A에서 B로 보내는 무선 전달 수단
  B보드 = 상태를 정리하고 펌프 작동을 결정하는 제어 담당자
  BLE = B보드와 스마트폰이 대화하는 무선 연결
  앱 = 사용자가 상태를 보고 명령을 내리는 조작 화면
  릴레이 = 작은 제어 신호로 움직이는 전기 스위치
  펌프 = 실제로 물을 이동시키는 장치
  LCD = 스마트폰을 보지 않아도 상태를 확인하는 작은 글자 화면

서로 다른 종류의 흐름을 구분하면 이해가 쉽습니다.
  정보 흐름: 센서 → A → 무선 → B → 앱/LCD
  명령 흐름: 앱 → BLE → B → 릴레이 제어 신호
  펌프 전력 흐름: 펌프용 전원 → 릴레이 접점 → 펌프
  물 흐름: 펌프 배관을 따라 이동하며, 전기선이나 통신선과는 다른 경로입니다.

A와 B가 따로 있다는 것은 역할을 나누었다는 뜻입니다.
측정부와 제어부를 각각 배치할 수 있고, 문제가 센서 쪽인지 출력 쪽인지 나누어 확인하기 좋습니다.
ESP-NOW를 쓰므로 두 보드 사이에 센서 전달용 신호선을 길게 연결할 필요가 없습니다.
ESP-NOW만 사용하기 위해 A와 B 사이에 GND선을 추가할 필요도 없습니다.
단, 각 보드에 직접 붙는 센서·모듈의 신호 기준 GND 연결은 별도로 필요합니다.

============================================================
2. 어떤 장치를 사용하고 있는가
============================================================

2-1. ESP32 A보드
  센서 측정과 ESP-NOW 송신을 담당합니다.
  현재 B가 받는 자료는 pH, 탁도 전압, 수위 부족 여부를 포함한 12바이트 묶음입니다.
  A의 원본 코드가 없으므로 실제 측정 주기·입력 핀·보정식은 확정할 수 없습니다.

2-2. ESP32 B보드
  A 센서값을 받고, BLE로 앱과 통신하고, LCD를 표시하고, 펌프 출력 신호를 만듭니다.
  현재 배포한 B 소스의 급수 출력은 GPIO16, 순환 출력은 GPIO17입니다.
  GPIO18은 기존 히터용 핀으로 HIGH를 유지하지만 새 프로그램은 히터 명령을 처리하지 않습니다.
  HIGH가 실제 히터 OFF라는 뜻은 아니므로 히터 부하 전원은 분리 상태로 둡니다.

2-3. pH 센서와 변환 모듈
  물이 산성인지 알칼리성인지 판단하는 데 사용하는 값을 만듭니다.
  일반적으로 pH 전극의 신호를 변환 모듈이 읽기 쉬운 전압으로 바꿉니다.
  전극을 ESP32 입력에 바로 꽂는 것과 전극용 변환 모듈의 출력을 읽는 것은 다릅니다.
  기존 로그에 pH 값이 들어왔다는 것은 통신 경로에서 숫자를 받았다는 증거입니다.
  그 숫자가 실제 물의 pH와 정확히 같다는 증거는 아닙니다. 기준 용액을 이용한 보정이 필요합니다.
  과거 저장소 문서에는 PH4502C가 나오지만 현재 실물 제품명으로 확정하지 않습니다.

2-4. 탁도 센서와 변환 모듈
  물의 흐림에 따라 빛의 통과·산란 등이 달라지는 현상을 전기 신호로 바꿉니다.
  센서 구조와 보정에 따라 출력 전압이 달라집니다.
  현재 Aquarium 경로의 turb 값은 전압 V입니다. 예를 들어 3.12는 3.12V라는 뜻입니다.
  이를 3.12NTU라고 읽으면 단위가 잘못됩니다. NTU는 보정된 탁도 단위입니다.
  과거 문서의 SEN0189는 참고 모델이며 현재 실물과 같은지 확인해야 합니다.

2-5. 수위 센서
  센서가 설치된 지점에서 물이 감지되는지를 나타내는 신호를 제공합니다.
  현재 A→B 자료의 waterLow는 1일 때 수위 부족, 0일 때 부족 아님입니다.
  B는 앱의 level 규칙에 맞춰 부족이면 0, 정상으로 보고하는 상태면 1로 바꿉니다.
  센서 한 개의 감지 결과만으로 수조 전체의 정확한 높이나 모든 위험 상태를 측정하지는 못합니다.
  현재 급수는 수동 제어이므로 수위 부족이 표시돼도 급수가 자동으로 켜지지 않습니다.
  반대로 물이 차도 급수를 자동으로 끄지 않습니다. 사용자가 직접 끕니다.
  실제 센서 선의 HIGH/LOW와 waterLow 값이 어떤 관계인지는 실제 A의 코드·센서 방향 확인이 필요합니다.
  과거 문서의 XKC-Y25-V는 현재 실물 확정 모델이 아닙니다.

2-6. 급수펌프와 순환펌프
  급수펌프는 물을 보충하는 용도로, 순환펌프는 물을 순환시키는 용도로 구분합니다.
  급수의 새 기능은 수동 끄기/켜기만 제공합니다.
  순환은 수동 끄기/켜기와 자동 시간 반복을 제공합니다.
  실제 펌프의 전압·전류·모델은 명판을 확인해야 합니다.
  과거 문서에는 급수 SZH-PWAT-040(12V DC), 순환 UP200(220V AC·20W)이 적혀 있습니다.
  그러나 현재 사용자의 실물 명판으로 확인한 값은 아닙니다.

2-7. 릴레이 모듈
  ESP32의 작은 신호로 펌프 전원 회로를 열거나 닫도록 하는 부품입니다.
  GPIO는 펌프를 직접 돌릴 만큼의 전력을 공급하는 단자가 아닙니다.
  펌프 전원은 별도로 공급하고 릴레이 접점을 스위치처럼 사용합니다.
  실제 릴레이 모듈 종류와 입력 호환성·정격은 확인해야 합니다.

2-8. LCD
  B의 현재 코드는 16칸×2줄 글자 화면을 사용합니다.
  순환 상태, pH/탁도, 수위/센서 연결, 급수 상태, 시간/BLE 상태의 5페이지를 약 3초마다 바꿉니다.
  LCD 글자가 보인다는 사실은 표시 장치가 작동한다는 증거입니다.
  LCD의 연결 문구만으로 펌프 회전이나 모든 센서의 정확도가 확인되는 것은 아닙니다.

2-9. 제외하거나 미확인인 장치
  수온 센서: 사용자가 제거하기로 했으며 현재 경로는 수온을 사용하지 않습니다.
  조도 센서: 저장소 A 코드에는 있지만 현재 12바이트 Aquarium 수신 자료에는 조도 필드가 없습니다.
             실제 장착·사용 중이라고 단정하지 않습니다. 이 경로에서는 조도를 전달하지 않습니다.
  산소 공급 장치: 앱/과거 코드에 관련 항목이 있어도 현재 Aquarium B에는 물리 산소 출력이 구현돼 있지 않습니다.
  히터: 현재 B 펌프 전용 코드의 제어 대상이 아닙니다. 앱에 카드가 남아 있어도 지원된다는 뜻이 아닙니다.

3. 전기 용어를 쉽게 설명하기
============================================================

전압(V)
  전기를 밀어주는 힘의 차이로 이해하면 됩니다. 부품이 요구하는 전압을 맞춰야 합니다.
  USB 5V, ESP32의 3.3V 논리, 펌프의 정격 전압은 서로 다른 이야기입니다.

전류(A)
  실제로 흐르는 전기의 양에 해당합니다.
  펌프처럼 모터가 있는 장치는 켜지는 순간 평소보다 큰 전류가 필요할 수 있습니다.
  펌프 전원·배선·릴레이를 정상 운전 전류만 보고 무조건 선택하면 안 됩니다.

전력(W)
  전기를 얼마나 사용하는지를 나타냅니다. DC에서는 전압×전류가 기본 관계입니다.
  AC 모터는 역률과 기동 특성도 있으므로 단순 숫자만으로 모든 정격을 판단하지 않습니다.

DC와 AC
  DC는 직류로 +/− 극성을 구분합니다. AC는 교류로 가정용 전원 등의 방식입니다.
  DC 펌프의 +/− 연결 그림을 AC 펌프에 그대로 적용하면 안 됩니다.

GPIO
  ESP32가 0/1 신호를 읽거나 내보내는 번호가 붙은 단자입니다.
  GPIO16이라는 숫자는 보드에 인쇄된 IO16/D16 등에 대응하는 신호 번호입니다.
  물리적으로 위에서 16번째 핀이라는 뜻은 아닙니다.

HIGH와 LOW
  디지털 신호의 높은 상태와 낮은 상태입니다. 일반적으로 ESP32 출력은 약 3.3V와 0V 수준입니다.
  HIGH가 언제나 펌프 켜짐은 아닙니다. 릴레이 입력 방식과 접점 배선에 따라 달라집니다.

VCC / GND / IN / OUT
  VCC: 해당 모듈의 전원 입력. 반드시 그 모듈의 정격에 맞춰 공급합니다.
  GND: 신호와 전원의 기준점. 일반 비절연 신호 연결은 같은 기준점이 필요합니다.
  IN: 모듈이 받는 입력 신호. 릴레이에서는 켜고 끄라는 제어선입니다.
  OUT: 센서 모듈 등이 내보내는 신호입니다.

공통 GND
  B와 일반 비절연 릴레이 제어측이 같은 '0V 기준'을 갖게 연결하는 것입니다.
  펌프 전력선과 제어선을 전부 한데 묶는다는 뜻이 아닙니다.
  건식 접점으로 스위칭하는 별도 DC 펌프 전원의 음극은 그 이유만으로 B GND에 연결할 필요가 없습니다.
  광절연 모듈의 JD-VCC·GND 분리 방법은 제품 회로에 따라 달라집니다.
  AC의 L/N/PE를 ESP32 GND·GPIO에 연결하지 않습니다.

ADC
  연속적으로 변하는 전압을 숫자로 바꾸는 기능입니다.
  예를 들어 저장소 A 코드는 12비트 ADC의 값을 0~4095 범위 숫자로 취급합니다.
  값이 들어왔다고 센서값이 자동으로 정확해지는 것은 아닙니다. 전압 범위·보정·노이즈가 중요합니다.

분압 저항
  두 저항으로 높은 신호 전압을 낮춰 입력하는 회로입니다.
  OUT - R1 - 측정점 - R2 - GND로 연결하고 측정점을 ADC에 연결합니다.
  측정점 전압 = OUT 전압 × R2 / (R1 + R2)
  저장소 문서의 R1=10kΩ, R2=20kΩ이면 5V는 약 3.33V가 됩니다.
  이는 3.3V 입력 한계에 대한 오차 여유가 작으므로 그대로 안전한 회로라고 단정할 수 없습니다.
  센서 최대 출력·저항 오차·입력 허용 범위를 확인하고, 회로가 달라지면 코드의 복원 배율도 바꿔야 합니다.

커패시터
  전압의 갑작스러운 변화와 잡음을 줄이는 데 사용합니다.
  신호선의 필터는 측정값 흔들림을 줄이고, 전원 쪽 디커플링은 전압 순간 변동을 줄이는 데 도움을 줍니다.
  전원 용량 부족이나 잘못된 접지를 커패시터 하나로 해결할 수 있다는 뜻은 아닙니다.

============================================================
4. 현재 B보드의 배선 연결을 설명하기
============================================================

아래 번호는 현재 B_board_Aquarium 소스 기준입니다.

  B GPIO16  → 급수 릴레이 입력 IN
                수동 OFF/ON. 설치할 때 실제 급수의 정지 신호 방향을 선택합니다.
                실물 IN 선이 해당 핀에 연결됐는지는 확인이 필요합니다.

  B GPIO17  → 순환 릴레이 입력 IN
                현재 관찰과 순환 실기 시험에서 LOW=정지, HIGH=작동입니다.
                수동 OFF/ON 또는 AUTO를 처리합니다.

  B GPIO18  → 기존 히터용 출력
                새 펌프 프로그램은 히터를 제어하지 않습니다.
                GPIO HIGH를 유지하는 것과 실제 히터 OFF는 같은 말이 아닙니다.

  B GPIO13  → LCD RS
  B GPIO14  → LCD E
  B GPIO27  → LCD D4
  B GPIO26  → LCD D5
  B GPIO25  → LCD D6
  B GPIO33  → LCD D7

  B GND     → 직접 연결되는 신호 장치의 기준 GND
                일반 비절연 릴레이/LCD 회로 기준이며 절연 모듈은 제품 회로를 따릅니다.
  전원      → B USB, 센서 모듈, LCD, 릴레이 모듈, 펌프의 정격을 각각 맞춥니다.

중요한 혼동:
  저장소 B_board/B_board.ino는 급수25·순환26·히터27을 사용하는 별도 설계입니다.
  현재 Aquarium B에서는 25/26/27이 LCD에 사용됩니다.
  예전 문서가 '확정'이라고 써 있어도 그 문서의 대상 코드가 무엇인지 먼저 봐야 합니다.

릴레이 채널에 IN1/IN2라고 적혀 있더라도 현재 실물에서 어느 채널을 쓰는지는 별도로 따라가 확인해야 합니다.
이 자료는 임의로 '급수는 반드시 CH1, 순환은 반드시 CH2'라고 확정하지 않습니다.

5. LCD 배선을 설명하기
============================================================

코드: LiquidCrystal lcd(13,14,27,26,25,33);

이 코드는 LCD에 들어가는 6개의 신호 핀 순서를 정합니다.
  첫 번째 13 = RS: 지금 보내는 내용이 글자인지 명령인지 구분
  두 번째 14 = E : LCD가 데이터를 받아들이는 시점
  나머지 27,26,25,33 = D4,D5,D6,D7: 글자·명령 내용을 전달

일반적인 HD44780형 16핀 LCD의 단자 번호로 표현하면 다음과 같습니다.
  4번 RS ← GPIO13
  6번 E  ← GPIO14
  11번 D4 ← GPIO27
  12번 D5 ← GPIO26
  13번 D6 ← GPIO25
  14번 D7 ← GPIO33

전원/부가 단자의 일반적 역할:
  1 VSS: GND
  2 VDD: LCD 정격 전원. 실제 제품 사양을 확인합니다.
  3 V0 : 글자 진하기 조정. 보통 가변저항으로 맞춥니다.
  5 RW : 쓰기 전용 사용에서는 GND
  7~10 D0~D3: 4비트 방식에서는 사용하지 않음
  15 A / 16 K: 백라이트. 내장 저항 유무와 제품 정격을 확인합니다.

4비트 방식을 쓴 이유:
  8개의 데이터선을 모두 쓰는 대신 4개 선으로 나누어 두 번 보냅니다.
  단순 글자 표시에는 충분하고 ESP32 핀을 줄일 수 있습니다.

lcd.begin(16,2)는 화면을 16칸×2줄로 초기화한다는 뜻입니다.
lcdLine()은 한 줄을 16칸으로 맞춰 이전에 길게 쓴 글자가 남지 않도록 합니다.
updateLcd()는 여러 정보를 페이지별로 번갈아 보여줍니다.

LCD가 5V 제품이라고 해서 ESP32에서 5V 신호가 나가는 것은 아닙니다.
전원 정격과 입력 HIGH 판정 전압은 서로 다릅니다. 3.3V 신호 호환성은 LCD 사양으로 확인합니다.
단자 번호도 실제 모듈 인쇄와 데이터시트를 우선합니다.

6. 릴레이와 펌프 전기 배선을 설명하기
============================================================

릴레이는 '제어측'과 '접점측'을 구분해야 합니다.

제어측:
  ESP32 GPIO → 릴레이 IN
  모듈 전원 → 릴레이 VCC/GND
  작은 신호로 모듈 안의 구동 회로와 코일을 작동시킵니다.

접점측:
  펌프용 전원 회로를 열거나 닫는 스위치입니다.
  접점 정격이 펌프 전압, AC/DC 구분, 모터의 기동 전류 등에 맞아야 합니다.
  릴레이 겉면의 한 가지 정격 숫자만으로 모든 DC/AC 모터 부하가 적합하다고 보지 않습니다.

COM / NO / NC:
  COM = 공통 접점
  NO  = 코일에 전원이 없을 때 COM과 연결되지 않는 접점
  NC  = 코일에 전원이 없을 때 COM과 연결되는 접점
  NO/NC의 '평상시'는 앱의 OFF 표시가 아니라 릴레이 코일이 쉬는 상태를 뜻합니다.

LOW 트리거 / HIGH 트리거:
  LOW 트리거는 낮은 IN 신호로 릴레이 구동이 활성화되는 방식입니다.
  HIGH 트리거는 높은 IN 신호로 구동이 활성화되는 방식입니다.
  접점이 NO인지 NC인지에 따라서 실제 펌프 전원 연결 결과는 다시 달라질 수 있습니다.

왜 예전에 앱 ON/OFF와 실제 동작이 반대였는가:
  원래 코드가 생각한 작동 신호와 실제 펌프의 작동 결과가 반대로 관찰됐습니다.
  그래서 현재 순환은 관찰된 결과에 맞춰 GPIO17 LOW=정지/HIGH=작동으로 맞췄습니다.
  원인이 릴레이 입력 극성인지 NC 접점 사용인지까지는 실물 연결 확인 전에는 확정할 수 없습니다.

그림 05의 DC 예시:
  정격 DC 전원 + → COM → NO 접점 → 펌프 +
  펌프 − → DC 전원 −
  이 예시는 NO 접점으로 전원을 끊는 일반적인 원리를 보여줍니다.
  현재 실물에 NO가 연결됐다는 뜻이나, 현재 펌프가 특정 전압의 DC 제품이라는 뜻은 아닙니다.
  DC 모터에는 제품과 구동 방식에 맞는 역기전력/서지 대책도 필요할 수 있습니다.

전원 구역을 분리하는 이유:
  펌프는 큰 전류와 잡음을 발생시킬 수 있고 ESP32는 작은 신호를 처리합니다.
  전력선과 센서 신호선을 구분하면 잘못된 전압 연결과 잡음 유입을 줄이는 데 도움이 됩니다.
  USB, 외부 5V, 보드 전원 핀을 임의로 병렬 연결하면 역급전이 생길 수 있으므로 보드 사양을 확인합니다.

AC 펌프가 사용되는 경우:
  명판과 절연·접지·보호장치·접점 정격을 확인해야 합니다.
  220V 배선은 감전 위험이 있으므로 전원을 차단하고 자격 있는 작업자가 시공해야 합니다.
  이번 그림은 AC 구역의 역할을 보여주는 원리도이며 전원코드 절단이나 임의 결선을 지시하지 않습니다.
  220V 선을 브레드보드나 ESP32 GPIO/GND에 연결하지 않습니다.
  앱 OFF와 전원 분리 상태는 다릅니다. 배선을 만질 때에는 실제 전원을 분리합니다.

7. 어떤 언어와 라이브러리를 썼고, 왜 썼는가
============================================================

Arduino C++
  ESP32에서 센서를 읽고 출력 핀과 통신을 직접 제어하는 데 사용합니다.
  setup()은 전원이 켜졌을 때 한 번 실행하는 준비 과정이고, loop()는 계속 반복하는 작업입니다.
  .ino는 Arduino 프로그램의 중심 파일, .h는 다른 파일에서 함께 쓰는 선언·규칙을 모아 둔 파일입니다.

LiquidCrystal
  병렬 문자 LCD를 제어하는 라이브러리입니다.
  글자를 표시할 때 필요한 전기 신호 순서를 직접 일일이 만들지 않고 사용할 수 있습니다.

NimBLE-Arduino
  ESP32의 BLE 통신 기능을 구현하는 라이브러리입니다.
  B가 센서 수신, LCD, 펌프 제어도 함께 하므로 자원을 비교적 적게 사용하는 BLE 구현을 사용합니다.

WiFi / esp_wifi / esp_now
  ESP32의 무선 기능과 채널을 설정하고 ESP-NOW 데이터를 받는 데 사용합니다.
  여기서 WiFi 기능을 켠다고 반드시 인터넷 공유기에 접속해야 한다는 뜻은 아닙니다.
  현재 B는 채널1로 맞춰 ESP-NOW 센서 자료를 받습니다.

driver/gpio.h
  GPIO 출력 래치를 직접 설정하는 데 사용합니다.
  새 B에서는 OFF 신호를 준비한 뒤 출력 핀을 활성화하고 다시 레벨을 적용합니다.
  초기화 순서 때문에 예상과 다른 신호가 나오는 일을 줄이기 위해 사용했습니다.

FreeRTOS 큐, portMUX, std::atomic
  통신 알림과 반복 작업이 서로 다른 실행 문맥에서 들어올 수 있어 순서를 정리하는 도구입니다.
  큐는 먼저 온 명령부터 보관하는 우편함, 잠금은 센서 묶음을 복사하는 동안 내용이 반쯤 바뀌지 않게 하는 장치로 이해하면 됩니다.
  atomic은 연결 상태 같은 작은 공유 표시를 여러 작업에서 다룰 때 사용합니다.

Dart / Flutter
  스마트폰 화면과 앱 동작을 만드는 언어·도구입니다.
  센서 표시와 버튼 같은 화면 구성을 재사용하기 쉽고 Android 앱으로 빌드할 수 있습니다.

flutter_blue_plus
  앱에서 BLE 기기 검색, 연결, 서비스 검색, 특성 읽기/쓰기/알림을 처리합니다.

JavaScript / HTML / esptool-js
  PC 브라우저에서 B보드 프로그램을 쓰거나 복원하는 도구에 사용합니다.
  HTML은 화면, JavaScript는 검증과 처리 순서, esptool-js는 ESP32 부트로더 통신을 맡습니다.
  Windows Edge/Chrome의 USB 시리얼 접근 기능을 사용하므로 Arduino IDE 없이 진행할 수 있습니다.
  이 도구는 실제 펌웨어를 쓰는 도구이며 단순 로그 보기와는 다릅니다.

Python
  배포용 HTML에 프로그램·라이브러리를 넣고 ZIP으로 묶거나 이번 그림을 만드는 데 사용합니다.
  B에서 펌프를 제어하는 실행 언어가 Python이라는 뜻은 아닙니다.

============================================================
8. 현재 B 코드: 파일별 역할과 읽는 순서
============================================================

8-1. B_board_Aquarium/B_board_Aquarium.ino
  전체 업무를 연결하는 중심 프로그램입니다.
  센서 수신 → 명령 처리 → 출력 → 상태 전송 → LCD 표시를 연결합니다.

  읽는 순서:
    (1) 맨 위 핀/UUID/설정 정의
    (2) setup(): 시작 준비
    (3) receiveSensor(): 센서 자료 확인
    (4) CommandCallbacks::onWrite(): 앱 명령을 큐에 넣음
    (5) loop(): 큐에서 꺼내 실제 제어 규칙에 적용
    (6) statusJson()/publishStatus(): 결과를 앱과 로그로 전달
    (7) updateLcd(): 작은 화면에 표시

  setup()의 중요한 순서:
    순환 GPIO17을 OFF 신호 LOW로 준비합니다.
    급수의 선택된 극성을 읽고 그 설정의 OFF 신호로 GPIO16을 준비합니다.
    출력 핀을 활성화한 후 신호 수준을 다시 적용합니다.
    시리얼과 LCD, ESP-NOW, 명령 큐, BLE 서비스를 시작합니다.

  receiveSensor()가 검사하는 것:
    등록한 A의 송신 주소와 같은지 확인합니다.
    길이가 정확히 12바이트인지 확인합니다.
    pH가 유한한 숫자이고 0~14인지, 탁도 전압이 0~5인지, 수위 값이 0/1인지 확인합니다.
    검사에 통과하면 최근 값과 수신 시각을 저장합니다.
    범위 검사는 잘못된 데이터를 거르는 것이며 센서 교정이나 실제 정확도 보증은 아닙니다.

  왜 수신 시각을 저장하는가:
    B가 최근 8초 동안 유효한 센서 자료를 받지 못하면 센서 연결을 오래된 것으로 봅니다.
    센서값은 null로 보내며 앱에서 이전 값을 계속 현재 실측처럼 표시하지 않도록 합니다.
    센서 통신이 끊겼다는 이유만으로 수동 급수/순환을 자동으로 끄는 로직은 없습니다.

  왜 명령을 큐에 넣는가:
    BLE 수신 콜백 안에서 모든 펌프 처리까지 하지 않고 loop()가 순서대로 처리하게 합니다.
    현재 큐는 최대 8개, 명령 저장 공간은 48바이트입니다.
    비어 있거나 너무 길거나 내부에 잘못된 종료 문자가 있는 명령, 꽉 찬 큐는 거부합니다.

  statusJson()은 무엇인가:
    앱이 읽기 쉬운 '이름:값' 묶음을 만듭니다.
    예: {"pump1Mode":1,"pump1On":true,"pin16":0}
    이 예시는 급수 설정이 HIGH=OFF일 때의 가능한 예시이지 모든 배선의 정답은 아닙니다.
    pump1Mode는 요청 모드, pump1On은 계산한 출력 상태, pin16은 읽은 GPIO 신호 수준입니다.

  publishStatus()의 이유:
    상태를 USB 시리얼 로그로 출력하고 BLE로 앱에 보냅니다.
    약 1초마다 또는 명령 처리 직후 상태를 보냅니다.
    긴 문자열을 20바이트씩 나눠 알리며 초기 읽기에는 전체 값을 유지합니다.
    BLE 알림 구독이 된 연결에 알림을 보내도록 구분합니다.

8-2. B_board_Aquarium/ManualSupply.h
  급수펌프의 단순한 규칙을 담습니다.

  핵심 코드:
    uint8_t mode=0;
    bool on(bool emergency=false) const {
      return configured() && mode==1 && !emergency;
    }

  쉬운 뜻:
    시작 모드는 끄기입니다.
    출력 방향 설정이 완료됐고 사용자가 켜기를 골랐으며 비상정지가 아닐 때만 ON으로 계산합니다.
    수위값이나 타이머는 이 조건에 들어 있지 않습니다.

  applySupply()가 받는 명령:
    pump1Mode=0 → 끄기
    pump1Mode=1 → 켜기
    pump1Mode=2 → 지원하지 않으므로 거부
    다른 숫자·잘못된 문장도 거부합니다.

  polarity는 왜 필요한가:
    같은 '끄기'라도 실제 배선에 따라 HIGH가 필요할 수도 LOW가 필요할 수도 있습니다.
    0: 설정 미완료. 급수 명령을 받지 않고 기존 HIGH를 유지합니다.
    1: HIGH가 OFF, LOW가 ON.
    2: LOW가 OFF, HIGH가 ON.
    설정 미완료의 HIGH를 실제 펌프 OFF라고 해석하면 안 됩니다.
    미설정 상태는 pump1Mode/pump1On을 null로 보내고 앱 급수 버튼을 활성화하지 않습니다.

8-3. B_board_Aquarium/Circulation.h
  센서 묶음의 형식 검사와 순환펌프의 모드·시간 계산을 담습니다.

  순환 모드:
    0 = 끄기
    1 = 켜기
    2 = 자동

  시작 값:
    mode=0
    onSeconds=120
    offSeconds=60
  즉 전원을 켜자마자 자동으로 돌리는 것이 아니라 OFF로 시작합니다.
  사용자가 AUTO를 선택하면 120초 작동, 60초 휴식을 반복합니다.
  앱의 circOn/circOff는 분 단위로 받고 B 내부에서는 초 단위로 바꿉니다.

  왜 긴 delay() 대신 millis()를 쓰는가:
    120초 동안 아무것도 하지 않고 기다리면 앱의 끄기 명령을 바로 처리하기 어렵습니다.
    millis()로 지난 시간을 계산하면 반복 작업을 계속 돌면서 다음 명령도 처리할 수 있습니다.
    완전히 지연이 없는 프로그램은 아닙니다. 작은 전송/반복 지연은 있지만 주기 전체를 막아 기다리지 않습니다.
    오랜 실행 뒤 시간 숫자가 한 바퀴 돌아가는 경우도 차이 계산으로 처리하고 테스트했습니다.

  step()의 첫 조건:
    if (mode!=2 || emergency) return;
  자동이 아니거나 비상정지면 자동 시간 계산이 수동 출력을 바꾸지 않는다는 뜻입니다.

  기존 C60/120 명령을 남긴 이유:
    원래 B의 자동 시간 명령과 일부 호환하기 위한 것입니다.
    원래 논리 ON/OFF와 실제 작동이 반대로 관찰됐기 때문에 현재 해석은 휴식60초/작동120초입니다.
    사용자는 보통 앱의 circOn/circOff와 모드 버튼을 사용하면 됩니다.

  E1/E0:
    E1은 두 펌프의 계산된 출력을 억제하는 비상 플래그입니다.
    E0은 해제입니다. 이전 ON 모드를 유지하므로 해제 시 다시 켜질 수 있습니다.
    이는 전원 차단 장치나 물리 안전 릴레이를 대신하는 기능이 아닙니다.

============================================================
9. 센서 데이터 묶음과 통신을 쉽게 설명하기
============================================================

현재 Aquarium의 A→B 묶음은 12바이트입니다.
  0~3번째 바이트: pH 숫자(float)
  4~7번째 바이트: 탁도 전압(float)
  8번째 바이트: 수위 부족 여부(0 또는 1)
  마지막 3바이트: 현재 B 수신 코드에서는 사용하지 않음

보내는 쪽과 받는 쪽은 순서와 크기를 같게 약속해야 합니다.
상자에 이름표 순서를 정해 넣는 것과 비슷합니다.
받는 쪽이 pH 자리에서 다른 숫자를 읽으면 값이 틀어질 수 있습니다.

static_assert(sizeof(SensorPacket)==12)는 컴파일할 때 이 크기를 확인합니다.
원래 A 소스를 확보한 것은 아니지만 B의 분석과 실제 수신 자료에 맞춰 이 형식을 유지합니다.

저장소 A_board/A_board.ino는 다른 형식입니다.
  조도(float), 탁도(float), pH(float), 수위(int32)의 16바이트입니다.
  저장소 B_board/B_board.ino는 이 16바이트와 예전 20바이트 형식을 받습니다.
  현재 B_board_Aquarium은 12바이트를 받습니다.
  따라서 저장소 A 소스를 현재 A에 바로 올리면 통신 형식이 달라 센서값을 받지 못할 수 있습니다.

BLE의 이름, 서비스, 특성:
  기기 이름 Aquarium은 사람에게 보여주는 이름입니다.
  서비스 UUID는 '수조 기능 묶음'을 찾는 주소 역할입니다.
  명령 특성은 앱이 명령을 넣는 칸, 상태 특성은 B가 결과를 내보내는 칸입니다.

  Aquarium 서비스: 4f7f1234-1234-5678-1234-aaaa00000001
  상태 읽기/알림: 4f7f1234-1234-5678-1234-aaaa00000002
  명령 쓰기:      4f7f1234-1234-5678-1234-aaaa00000003

초기에 연결이 안 됐던 이유:
  휴대폰과 B의 무선 연결 자체는 됐어도 앱이 찾던 서비스 주소가 원래 B와 달랐습니다.
  맞는 Aquarium 서비스와 쓰기/알림 특성을 찾도록 수정했습니다.

연결 뒤에도 순환 제어가 안 됐던 이유:
  원래 B는 받은 문자열을 로그에 출력했지만 pump2Mode=0/1/2를 해석하지 않았습니다.
  '명령을 받았다'와 '그 명령을 실제로 처리했다'는 서로 다른 단계입니다.
  새 B에서 앱의 모드 명령을 처리하고 적용 상태를 돌려주도록 바꿨습니다.

긴 JSON이 나뉘는 이유:
  BLE 한 번의 전송에 담을 수 있는 크기가 제한되므로 긴 상태를 조각내 보낼 수 있습니다.
  앱의 ble_manager.dart는 조각을 모아 완성된 JSON인지 확인한 뒤 전달합니다.
  조각 로그만 보고 센서 자체가 고장이라고 판단하면 안 됩니다.

10. 앱 코드를 쉽게 설명하기
============================================================

app/flutter_app/lib/ble_manager.dart
  기기를 찾고 연결하고 서비스/특성 주소를 확인하는 통신 담당입니다.
  두 종류의 지원 서비스 구성을 구분하고 명령 쓰기와 상태 알림 역할을 확인합니다.
  상태 조각을 모아 JSON으로 해석하고 진단용 수신 기록을 남깁니다.
  write()는 명령 끝에 줄바꿈을 붙여 BLE로 보냅니다.

app/flutter_app/lib/aqua_api.dart
  통신 결과와 화면 조작을 연결하는 담당입니다.
  사용자가 원하는 값과 보드가 실제로 회신한 값을 구분합니다.
  BLE 쓰기 응답만 오면 '확인 대기', 새 상태에서 같은 모드가 오면 '보드 설정값 확인됨'으로 바꿉니다.
  일정 시간 같은 설정이 오지 않으면 적용 미확인으로 표시합니다.
  급수는 0/1만 보내고 Aquarium의 manualSupplySupported가 true일 때만 사용할 수 있게 합니다.
  데모 모드에서도 수위가 부족하다고 급수펌프가 자동으로 켜지지 않도록 바꿨습니다.

app/flutter_app/lib/models.dart
  센서값, 모드, 출력 상태 등을 정리하는 기록장입니다.
  water_low를 앱의 level 규칙으로 바꾸고, 숫자가 실제 수신됐는지도 기억합니다.
  null은 0이나 정상이라는 뜻이 아니라 '확인할 수 없는 값'으로 처리합니다.
  현재 새 B의 pump2On 같은 명시적인 출력 상태를 우선합니다.
  과거 Aquarium의 cir 표시 반대 문제를 보정하는 호환 처리도 남아 있습니다.

app/flutter_app/lib/control_tab.dart
  급수·순환 등의 제어 카드를 화면에 그립니다.
  급수에는 끄기/켜기 두 선택지만 있고 순환에는 자동까지 있습니다.
  급수 지원 설정을 받지 못하면 버튼을 비활성화하고 B 업데이트/출력 설정 안내를 보여줍니다.
  앱에 히터 카드가 보이더라도 현재 B 펌웨어가 히터를 지원한다는 뜻은 아닙니다.

app/flutter_app/lib/monitor_tab.dart
  수신된 센서 상태를 사용자에게 보여주는 화면입니다.
  현재 앱 v1.3.8의 Aquarium 탁도 칸은 숫자를 표시하고 단위 글자는 비워 둡니다.
  B JSON은 turbUnit="V"를 보내고 B LCD에는 V를 표시합니다.
  따라서 앱 화면에 V가 인쇄돼 있다고 설명하지 말고, 수신값의 의미가 전압 V라고 설명합니다.
  pH 화면 경고 기준 6.5/7.5는 앱의 기본 표시 기준이며 모든 수조 생물의 적정 범위를 보장하지 않습니다.

중요한 표현 차이:
  '명령 전송됨' = 무선으로 쓰기 단계가 진행됨
  '보드 설정 확인됨' = B가 같은 모드를 다시 알려줌
  '보드 ON' = B가 계산한 출력 상태가 ON
  '실제 펌프 작동 확인' = 사람이 회전·물 이동을 확인하거나 별도 회전/유량 센서로 확인
현재 장치에는 펌프의 실제 회전·유량을 확인하는 센서가 구현돼 있지 않습니다.

  새 B 소스는 백업 분석에 맞춰 다시 작성한 것이며 원본 Arduino 소스를 완전히 복원했다고 주장하지 않습니다.

12. 저장소 A 코드의 측정 방식 — 현재 실기와 별도 참고
============================================================

아래는 A_board/A_board.ino를 이해하기 위한 설명입니다.
현재 실기 A의 원본 소스라고 단정하거나 그대로 업로드하지 않습니다.

정의된 센서 핀:
  조도 GPIO33 / 탁도 GPIO32 / pH GPIO34 / 수위 GPIO35
  수온 GPIO4 사용은 제거됐습니다.

analogAvg(pin,16)
  같은 아날로그 입력을 16번 읽고 평균을 냅니다.
  한 번 읽을 때 순간적으로 튀는 값을 완화하려는 목적입니다.
  잘못된 회로·센서 고장·보정 오차까지 없애 주는 기능은 아닙니다.

ADC1 핀을 고른 이유
  이 코드의 아날로그 핀은 ESP32 ADC1 계열을 사용합니다.
  무선 기능을 함께 사용할 때 ADC2 사용 제약을 피하려는 설계입니다.

탁도 코드
  raw/4095×3.3×DIV_TURB로 센서 전압을 계산한 다음 경험식을 통해 NTU를 추정합니다.
  DIV_TURB=1.5는 문서의 분압 배율을 되돌리는 값입니다.
  이 경험식과 전압 환산은 센서·보정·회로 조건에 의존하며 실제 정확도는 따로 검증해야 합니다.
  현재 Aquarium B는 이 NTU 계산 결과 대신 탁도 전압을 받는 다른 경로입니다.

pH 코드
  7.0 + ((기준 전압 - 측정 전압) / 기울기) + 보정값으로 계산합니다.
  이 파일의 기준 전압은 2.50V, 기울기는 0.18, 추가 보정값 기본은 0입니다.
  이 숫자가 모든 전극에 맞는 것은 아닙니다. 실제 센서로 보정해야 합니다.
  0~14로 제한하는 것은 표시 범위를 제한하는 것이며 센서가 정확해진다는 뜻은 아닙니다.

조도 코드
  ADC 비율을 0~100%로 표시합니다. 변수 이름이 lux여도 실제 조도 단위 lux로 보정한 값은 아닙니다.

수위 코드
  입력 LOW를 물이 감지된 상태로 해석해 정상=1로 바꿉니다.
  이 반전 규칙은 이 소스의 가정이며 실제 A의 입력 극성이라고 확정하면 안 됩니다.

반복 주기
  이 저장소 A 코드는 약 2초마다 측정·LCD 갱신·송신을 합니다.
  현재 실기 A도 반드시 2초마다 동작한다는 의미는 아닙니다.

14. 문제를 발견했을 때 구분하는 순서
============================================================

센서값이 안 보임:
  A 전원 → 센서 전원/신호 → A의 실제 측정 로그 → ESP-NOW 채널/송신 필터 → B 수신 → BLE → 앱 표시 순서로 구분합니다.
  앱 값이 없다는 사실만으로 센서 고장이라고 바로 결론 내리지 않습니다.

수위가 실제와 다르게 보임:
  센서 설치 위치/방향 → 실제 출력 신호 → A가 그 신호를 해석한 값 → B waterLow → 앱 level 순서로 봅니다.
  수신된 0/1이 무엇을 뜻하는지부터 맞춥니다.

버튼은 눌리는데 펌프가 안 바뀜:
  앱 명령 → B의 [BLE CMD] → [CMD APPLIED]/[CMD REJECTED] → 회신 모드 → GPIO → 릴레이 → 펌프 전원 순서입니다.
  실제 물 이동은 마지막 단계에서 따로 확인합니다.

켜기/끄기가 반대로 보임:
  앱의 논리 상태, GPIO HIGH/LOW, 릴레이 트리거, NO/NC 접점을 각각 구분합니다.
  화면만 반전시키면 실제 제어 문제가 해결되는 것은 아닙니다.

순환은 되지만 새 급수 버튼이 비활성화됨:
  앱 v1.3.8인지, B 상태의 firmware가 Aquarium-pumps-1.1.0인지,
  manualSupplySupported가 true인지, 급수 극성 설정이 완료됐는지 확인합니다.

15. 발표에서 사용할 정확한 결론
============================================================

이 시스템은 센서 정보의 무선 전달과 스마트폰 펌프 제어를 결합했습니다.
현재 확인된 센서 경로는 pH·탁도 전압·수위 상태입니다.
급수는 사용자가 원할 때만 켜고 끄는 수동 방식이며 순환은 수동/자동을 제공합니다.
순환은 사용자의 실기 확인을 받았고, 급수의 새 기능은 코드·앱·모의 설치 검증과 배포를 마쳤습니다.
급수의 실제 설치·회로·작동, 센서의 정확도 보정과 실제 A 핀은 추가 확인 대상입니다.

“모든 센서가 정확하다”, “앱 ON이면 물이 반드시 흐른다”, “급수는 물이 차면 자동으로 꺼진다”,
“저장소의 모든 그림이 현재 실물 배선이다”라는 표현은 현재 근거와 맞지 않습니다.
